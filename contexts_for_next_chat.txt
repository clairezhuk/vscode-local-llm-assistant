Project Essence

A local AI programming assistant built as a VS Code
extension.

  - Resources: Optimized for entry-level hardware (2GB VRAM, 8GB RAM). Utilizes
    quantized Qwen 2.5 Coder 1.5B via llama.cpp with a restricted context window
    (2048 n_ctx) and reduced batch size (128 n_batch) for CUDA stability.
  - Key Features: Real-time streaming chat, Agentic Thinking workflows,
    concurrency management for shared GPU access, and human-in-the-loop terminal
    execution.
  - VRAM & Context Management: Solved the 2048 token bottleneck by implementing a prioritized context stack: (1) System Instructions, (2) Current User Query + File Context, (3) Sliding History Window.

Class Responsibilities

Frontend (VS Code Extension - TypeScript):
  - chat_view.ts (ChatViewProvider): Manages the Webview UI. Implements
    JSON-stream buffering (protection against fragmented chunks), passes the
    workspace directory path to the backend, and handles the AbortController for
    safe generation interruption.
  - ghost_text.ts (GhostTextProvider): Provides inline code completions.
    Operates via the backend's request queue, functioning alongside the chat.
  - Webview Script: Handles real-time markdown rendering and interactive UI
    elements like Accept/Reject buttons for terminal commands.

Backend (FastAPI - Python):
- engine/llm.py (LLMEngine): The core engine. A wrapper for llama.cpp optimized for low-resource environments (2GB VRAM). Configured with a 2048 context window (n_ctx) and reduced batch size (n_batch=128) for CUDA stability.
- agentic_orchestrator/orchestrator.py (Orchestrator): The "Managing Director." Handles the request lifecycle: query preprocessing (cleaning/translation), file context aggregation, technical Goal Analysis, and high-level routing between modules.
- agentic_orchestrator/reasoning.py (ReasoningEngine): The "Thinker." Implements various reasoning strategies (Fast Mode, Recursive Thinking, Planning, Reflection-Refine). Manages iterative attempt cycles and intent-specific logic (Learn, Code, Terminal).
- agentic_orchestrator/validator.py (Validator): The "Critic." Provides dual-stage verification: static code analysis (via ast.parse) and LLM-based logical verification to ensure the output meets the defined Goal.
- agentic_orchestrator/prompts.py (PromptLibrary): A centralized repository for all system instructions. Ensures persona consistency and allows for rapid tuning of AI behavior without modifying core logic.
- context_manager/manager.py (ContextManager): The "Memory Manager." Implements an intelligent sliding window for dialogue history. Strictly enforces character limits (~8000 chars) to prevent context overflow and maintain 2048 n_ctx stability.
- context_manager/file_processor.py (FileProcessor): Smart contextualization system. Instead of loading raw files, it performs "Structural Extraction" (code signatures/function names) or "Semantic Summarization" for large files to preserve context within token limits.
- executor/tools.py (ToolExecutor): Executes terminal commands within the user's specific workspace context, supporting human-in-the-loop verification (Accept/Reject).

Current State

An Agentic Reasoning Pipeline is implemented, allowing the 1.5B model to solve
complex tasks through self-critique:

1.  Concurrency Safety (GPU Locking): Implemented a locking mechanism
    (asyncio.Lock). Requests from Ghost Text and Chat are queued, preventing
    CUDA crashes during simultaneous VRAM access.
2.  Fast Mode: Direct response generation for simple questions and quick
    instructions.
3.  Thinking Mode (Recursive Chain-of-Thought):
      - Goal Analysis: The model first formulates a concise goal to maintain
        "focus" throughout the entire cycle.
      - Iterative Critique: Every response is verified (logically or via
        ast.parse). If the result fails to meet the goal, the error reason is
        fed back into the next iteration (up to 3 attempts).
      - Code Assembly: For coding tasks, the system generates fragments based on
        a plan. A final "Architect" stage assembles these fragments into a
        single file, removing duplicate imports and functions.
      - Attempt Transparency: The UI displays all reasoning cycles and attempts
        separated by headers, allowing the user to compare different versions.
4.  Robust Streaming: The frontend utilizes a text buffer to collect fragmented
    JSON packets, ensuring smooth text rendering even during unstable generation
    speeds.
5.  Safe Terminal: Commands are generated based on environment constraints,
    displayed for user verification, and executed strictly within the project's
    working directory.

Testing System (Benchmarks)

An automated sandbox designed to verify architectural stability and reasoning
quality.

  - Structure: Thematic test suites (Algorithms, CLI, Logic).
  - Runner: Creates isolated temp directories, executes generated code, and
    verifies results via assert statements. Supports real-time CSV logging and
    manual mode selection (fast vs. thinking).
  - Metrics: Focuses on the Self-Correction Success Rate (success after
    retries), processing time.
  - Warning Detection: Automatically detects if the AI output contains a
    "Warning" badge, indicating failed internal verification.
  - Running from Docker

Technical Constraints & Solutions

  - VRAM Limit (2GB): Solved by reducing n_ctx to 2048 and n_batch to 128. This
    prevents "Out of Memory" errors during deep reasoning cycles.
  - Thread Safety: Resolved using asyncio.to_thread for the execution of
    synchronous llama_cpp calls and a global asyncio.Lock within the
    Orchestrator, making the local server stable under parallel requests from VS
    Code.
  - Instruction Adherence: Addressed by strictly limiting tokens in planning
    stages and using specialized system prompts to prevent the 1.5B model from
    looping or repeating instructions.

Data Analysis System

A specialized evaluation pipeline (analysis.py) that transforms benchmark 
CSV logs into a 12-file diagnostic report stored in versioned 
results/analysis/analysis_vN/ folders.

  - 0_text_stats.txt: Detailed log of per-mode performance. Reports 
    Full/Partial test counts, attempt-level success %, Warning Efficiency 
    (Correct Warnings / Total Fails), and Interference (Wrong Warnings / 
    Total Successes).
  - 1_general_heatmap.png: Categorical grid showing pass levels (100%, >50%, 
    Partial, Fail) and self-correction markers. Includes a numeric Y-axis 
    for all test indices, fine-grained grid lines, and a color-coded legend.
  - 2_percentage_heatmap.png: Continuous gradient (Red-Yellow-Green) mapping 
    exact success ratios. Uses NaN-masking to keep cells for non-existent 
    tests black (background color).
  - 3_bars_by_suite.png: Success ratio comparison (0.0–1.0) grouped by 
    test suite blocks (e.g., Algorithms, CLI) using a fixed mode order.
  - 4_bars_by_intent.png: Success ratio comparison segmented by request 
    complexity: Theory (1), Coding (2), and CLI (3).
  - 5_latency_by_mode.png: Boxplots showing processing time (time_s) 
    distribution per mode to identify median speed and VRAM-related outliers.
  - 6_latency_by_suite.png: Segmented boxplots evaluating how different 
    thematic blocks (e.g., Logic vs. Shell) impact generation duration.
  - 7_latency_by_intent.png: Boxplots comparing processing time specifically 
    across Theory, Coding, and CLI tasks.
  - 8_conf_matrix_all.png: Warning Confusion Matrix for all tests. Maps 
    TP (Warn/Fail), TN (NoWarn/Pass), FP (Warn/Pass), and FN (NoWarn/Fail).
  - 9_conf_matrix_coding.png: Specialized Confusion Matrix identical to #8 
    but isolated to Intent 2 (Coding) to measure code-specific critique accuracy.
  - 10_warning_proportions.png: Bi-directional bar chart. Positive Y-axis 
    (Blue-Green) shows Correct Warning rates; negative Y-axis (Orange-Red) 
    shows False Positive (Wrong Warning) rates per suite.
  - 11_response_effectiveness.png: "Model Honesty" chart. Measures the 
    rate of attempts that were either correct OR correctly flagged as wrong 
    by the internal critique logic.

All visualizations strictly follow the hierarchy: 
Fast -> Planning -> Chain of Draft -> Reflection_refine.
